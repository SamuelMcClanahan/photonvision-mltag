## Items (review text)
### A1: An interrupt of the waiting thread makes awaitResult give out a frame that a lane and the work thread still use; the frame is released under them and a false zero-target result is published
- Location: <scratch>/wt/photon-core/src/main/java/org/photonvision/vision/pipeline/AprilTagPipeline.java:426
- Failure scenario: PV_MLTAG_INFERENCE_LANES=2 (Orange Pi run script). The user deactivates or removes a camera: VisionModule.stop() -> VisionRunner.stopProcess() -> visionProcessThread.interrupt(). The interrupt flag stays set through frameSupplier.get() (native grab does not react). In the next pipeline.run(), awaitResult() calls pending.result().get() for a frame that is not complete (in the one-frame-at-a-time mode this is ALWAYS the case, because the frame was submitted microseconds before). FutureTask.get() throws InterruptedException immediately. awaitResult() then returns new CVPipelineResult(seq, 0, 0, List.of(), pending.frame()). VisionRunner gives this result to the consumers: (1) NTDataPublisher publishes a result with zero targets and a valid capture timestamp for a picture that can contain tags; (2) VisionModule.consumeResult() releases the frame (or gives it to the stream thread) while the lane thread is in detector.detect() (letterbox reads the Mat) and before the work thread decodes it. For a GStreamer frame, release puts the pixel buffer back into the native pool (or frees it), so the lane reads memory that the capture thread writes again or that is unmapped: wrong pixels or a native crash that stops all cameras. The same early return happens in discardPendingFrames() when the calling thread is interrupted (release(), setPipeParamsImpl): then frameWorker.shutdownNow(), lane.release() (model destroyed) or lane.setParams() run while a lane is in inference.
- Evidence: AprilTagPipeline.java 432-437: `catch (InterruptedException e) { Thread.currentThread().interrupt(); } ... return new CVPipelineResult(pending.frame().sequenceID, 0, 0, List.of(), pending.frame());` - the future is not done, but the Javadoc says 'Always returns a result that owns the frame'. Same pattern in finishFrame 414-417: the flag is set again BEFORE detection.await(), and PendingDetection.await() (AprilTagMLHybridPipe.java 104-112) catches InterruptedException from future.get() and returns, so it does not wait when the flag is set. Same pattern in estimateSingleTagPoses 673-684: after the first InterruptedException the flag is set again, each next future.get() throws immediately, but the comment at 686 says 'All tasks are complete here'. VisionRunner.stopProcess() (line 123) is the interrupt source. AprilTagROIDecodePipe.processParallel (263-272) already does this correctly (waits for all futures, then sets the flag).
- Method from the review (use it unless the "Decisions" section above says something different): Make each wait for work that uses a frame uninterruptible. (1) AprilTagPipeline.awaitResult(PendingFrame): loop `while (true) { try { result = pending.result().get(); break; } catch (InterruptedException e) { interrupted = true; /* continue to wait */ } catch (ExecutionException | CancellationException e) { log; break; } }`, and in a finally block call Thread.currentThread().interrupt() if `interrupted` is true. The method must never return while the future is not done. (2) AprilTagMLHybridPipe.PendingDetection.await(): the same loop on future.get() (end the loop on normal return, ExecutionException or CancellationException; set the interrupt flag again after the loop). (3) AprilTagPipeline.finishFrame(): in the InterruptedException branch call detection.await() first and Thread.currentThread().interrupt() after it; change the second catch to Throwable so no failure returns before the lane is done. (4) AprilTagPipeline.estimateSingleTagPoses(): in the loop over `futures`, when future.get() throws InterruptedException, remember it and call get() again on the SAME future until it is done; set the interrupt flag after all futures are done. Test (AprilTagPipelineInferenceLanesTest): TestPipeline(2, new SimulatedModel(300)); start a thread that calls pipeline.run(frame) and stores the result and Thread.currentThread().isInterrupted(); sleep 100 ms; interrupt the thread; join. Assert: model.inferences.get() == 1 at the time run() returned (the inference ended before the return), result.targets.size() == tagBoxes.size() (the real result, not an empty one), frame.colorImage.isReleased() is false before the test releases the result, and the interrupt flag was still set. With the current code run() returns immediately with 0 targets and inferences == 0.

### A2: Capture timestamp of DriverMode, Calibrate3d and Focus results changed: it is now the construction time of the output Frame, not the capture time of the camera frame
- Location: <scratch>/wt/photon-core/src/main/java/org/photonvision/vision/pipeline/CVPipeline.java:91
- Failure scenario: The camera is in driver mode (drivers switch it on in a match), in 3D calibration, or in the focus pipeline. Each of these pipelines returns a result with a NEW Frame object made with the constructor that has no timestamp argument, so its timestampNanos is MathUtils.wpiNanoTime() at the end of processing. Base code: result.setImageCaptureTimestampNanos(frame.timestampNanos) with the INPUT frame. New code takes the timestamp from result.inputAndOutputFrame, which is that new Frame. Result: the capture timestamp that NTDataPublisher sends (captureMicros) and the latency (NT latencyMillis, UI latency) are wrong for these three pipelines: the capture time is too late by the full capture-to-result time and the latency shows almost 0 ms. VisionRunner.recordTiming gets the same wrong frame: captureToPipelineDoneMs is almost 0 and the GStreamer estimated age is lost (metadata 'unknown') in these modes.
- Evidence: CVPipeline.java 91-92: `Frame resultFrame = result.inputAndOutputFrame != null ? result.inputAndOutputFrame : frame; result.setImageCaptureTimestampNanos(resultFrame.timestampNanos);` (base: `result.setImageCaptureTimestampNanos(frame.timestampNanos);`). DriverModePipeline.java 88-93, Calibrate3dPipeline.java 154-159, FocusPipeline.java 84-89: `new Frame(frame.sequenceID, ..., frame.frameStaticProperties)` -> Frame.java 84-91 uses MathUtils.wpiNanoTime(). VisionRunner.java 294-302 uses the same result frame for resultFrameTimestampNanos and resultEstimatedAgeNanos. Reflective, ColoredShape, Aruco, ObjectDetection and AprilTag return the input frame, so they are not affected.
- Method from the review (use it unless the "Decisions" section above says something different): Keep the base rule (timestamp of the input frame of the call) for all pipelines, and let only the pipeline that can return a result of an earlier frame say which frame the result is from. In CVPipeline add `public Frame getResultSourceFrame(R result, Frame inputFrame) { return inputFrame; }` and in run() use `result.setImageCaptureTimestampNanos(getResultSourceFrame(result, frame).timestampNanos);`. In AprilTagPipeline override it: `return result.inputAndOutputFrame != null ? result.inputAndOutputFrame : inputFrame;` (AprilTagPipeline always puts the frame that the result was computed from into the result). In VisionRunner.update() replace the local computation at 294-302 with `Frame resultFrame = pipeline.getResultSourceFrame(pipelineResult, frame);` (or: use pipelineResult.getImageCaptureTimestampNanos() as the timestamp and take captureMetadata from pipelineResult.inputAndOutputFrame only if its timestampNanos is equal to that value, else from `frame`). Test: new unit test that runs DriverModePipeline (and FocusPipeline) with `new Frame(7, color, processed, FrameThresholdType.NONE, 123_456_789L, props)` and asserts result.getImageCaptureTimestampNanos() == 123_456_789L; it fails with the current code. The existing assertion in AprilTagPipelineInferenceLanesTest (capture time == timestamp of result.inputAndOutputFrame) must continue to pass.

### A3: After the frame rate drops, results stay one or more frames late: the stale-frame discard can leave frames in work while the controller is reset to one-frame-at-a-time (permanent), and the normal exit from OVERLAP needs about 85 calls
- Location: <scratch>/wt/photon-core/src/main/java/org/photonvision/vision/pipeline/AprilTagPipeline.java:441
- Failure scenario: Orange Pi, 2 lanes, 60 FPS, inference 23 ms: the pipeline is in OVERLAP with 2 or 3 frames in work. Robot code sets the NT FPS limit (VisionRunner.waitUntilNextTick) to 3 FPS. Call 1 after the limit: pending [A, B], new frame C is 333 ms newer; nothing is stale; A is returned. Call 2: frame D; B is 683 ms old -> discarded; C is 333 ms old -> kept; overlapController.reset() puts the controller in SERIAL mode with pendingFrames = [C]. In SERIAL mode onFrame() always returns COMPLETE_OLDEST, so each call submits its frame and returns the frame before it: C with call D, D with call E, without end. Each published result is one limit period (333 ms) older than necessary, the log line says 'one frame at a time', and nothing drains the queue (the low-idle condition to start OVERLAP again is never true at 3 FPS). With depth 3 and 5 FPS two frames stay: 400 ms late permanently. The condition is: oldest pending frame older than 500 ms, a newer pending frame not. Second symptom, without a stale frame: FPS limit 10 with depth 2 gives results that are 200 ms late for about 85 calls (8.5 s; 17 s and 400 ms at 5 FPS), because the exit needs more than 24 of the 32 period samples to be long and then 60 calls in sequence (CALLS_TO_STOP_OVERLAP). The base code returns the result of the input frame in each call.
- Evidence: AprilTagPipeline.java 443-454: the while loop stops at the first frame that is not stale, then `if (discarded && overlapController != null) overlapController.reset();` with frames still in pendingFrames. InferenceOverlapController.reset() (258-270) sets overlap=false; onFrame() 171-217: in the not-overlap branch there is no check of pendingFrames, line 217 returns COMPLETE_OLDEST. processWithInferenceLanes 383-394: addLast(new frame), removeFirst() -> the older frame is returned. Slow exit: InferenceOverlapController 196-200 (lower quartile of 32 samples, streak of 60).
- Method from the review (use it unless the "Decisions" section above says something different): Part A (AprilTagPipeline.discardStalePendingFrames): if the oldest pending frame is stale, discard ALL pending frames: replace the loop body with one call to discardPendingFrames() (it waits, releases and resets the controller) and write the warning one time. The SERIAL mode of the controller is only valid with an empty queue. Add a guard in processWithInferenceLanes after onFrame(): if `!overlapController.isOverlapActive() && !pendingFrames.isEmpty()` then log a warning and call discardPendingFrames() before the input frame is submitted. Part B (InferenceOverlapController, OVERLAP branch of onFrame): add a fast exit for a long frame period. Keep the last valid period in a field `lastFramePeriodNanos` (set in updateFramePeriod, 0 for no sample). `longPeriodStreak = (inferenceSamples > 0 && lastFramePeriodNanos > 2.0 * workNanos) ? longPeriodStreak + 1 : 0;` When it is 3: set knownCameraPeriod = lastFramePeriodNanos, set the streak counters to 0, and leave OVERLAP the same way as at line 200-208 (leavingOverlap = true and return SKIP_INPUT if pendingFrames > 0, else overlap = false). Set longPeriodStreak to 0 in reset() and when OVERLAP starts. An overloaded pipeline does not trigger this: its frame period is about work/lanes, which is less than the work time. Tests: (1) AprilTagPipelineInferenceLanesTest: TestPipeline(2, SimulatedModel(30)); 40 calls with frame timestamps 16.7 ms apart (assert the last result is not for the input frame); then 12 calls with timestamps 300 ms apart (sleep 300 ms between calls); assert that from the 5th slow call each result is non-null and result.inputAndOutputFrame == the input frame. Current code: never the input frame. (2) InferenceOverlapControllerTest: bring the controller to OVERLAP depth 2 (60 FPS timestamps, inference 23 ms, post 4 ms), then give frames 200 ms apart with pendingFrames=2: assert SKIP_INPUT at the 3rd slow frame and isOverlapActive()==false after pendingFrames reaches 0; and the existing overload test (period 33 ms, work 50 ms) must not leave OVERLAP.

### A6: release() from the DataChangeEvent thread (a race that is also in the base) can now leave the vision thread blocked without end, and can release the models while a lane is in inference
- Location: <scratch>/wt/photon-core/src/main/java/org/photonvision/vision/pipeline/AprilTagPipeline.java:741
- Failure scenario: Robot code changes the pipeline index through NT (NT thread sets PipelineManager.requestedIndex). ### A8: Results of the frames in work are published only when a new camera frame arrives: they are lost when the camera stops for more than 500 ms
- Location: <scratch>/wt/photon-core/src/main/java/org/photonvision/vision/pipeline/AprilTagPipeline.java:393

When the next frame arrives more than 500 ms later, discardStalePendingFrames releases them and they are not published. In the base behavior each frame was published before the next frame was taken. For a stop shorter than 500 ms the three results are published late by the length of the stop.
- Evidence: A result leaves the pipeline only as the return value of processWithInferenceLanes (lines 393-396). VisionRunner.java lines 259-272 do not call the pipeline for an empty frame or for a disabled camera. AprilTagPipeline.java lines 443-448 release stale frames with no publication.
- Method from the review (use it unless the "Decisions" section above says something different): Add `public R pollCompletedResult() { return null; }` to CVPipeline. Override it in AprilTagPipeline: if pendingFrames is not empty and `pendingFrames.peekFirst().result().isDone()`, remove the first entry, get its result with awaitResult, call `result.setImageCaptureTimestampNanos(result.inputAndOutputFrame.timestampNanos)` and return it; else return null. Do not call the controller in this method (with the final decision of the first finding the controller returns DEFER later until the depth is filled again). In VisionRunner.update, in the empty-frame branch and in the disabled branch, before the blank result: `CVPipelineResult done; while ((done = pipeline.pollCompletedResult()) != null) pipelineResultConsumer.accept(done);`. Test in AprilTagPipelineInferenceLanesTest: bring the pipeline to overlap (30 ms model, 2 lanes), sleep 100 ms with no call, then call pollCompletedResult() until it returns null: the number of results must be the number of calls that returned null before, the sequence IDs and capture times must increase and be equal to those of their frames, and each frame must be released after result.release().
