## Items (review text)
### D1: The global open lock is held during the new first-frame wait, so one camera that opens but gives no frame blocks the open of the other camera for about 50 seconds
- Location: photon-core/src/main/java/org/photonvision/vision/frame/provider/GStreamerUSBFrameProvider.java:127
- Failure scenario: Two cameras. Camera A is present but gives no frame (bad cable or USB power, or it does not have the video mode of the environment variables: v4l2src reaches PLAYING as a live source and then fails with not-negotiated). The vision thread of A takes the static CAPTURE_OPEN_LOCK first. With the script defaults it tries 3 io-modes x 2 candidates (direct, legacy) x 3 attempts = 18 attempts. Each attempt waits PV_USB_GSTREAMER_FIRST_FRAME_TIMEOUT_MS = 2500 ms in openCandidate(), plus 250 + 500 ms sleeps for each candidate. All this is inside synchronized (CAPTURE_OPEN_LOCK): about 18 x 2.5 s + 6 x 0.75 s = 49.5 s. During this time the vision thread of the good camera B is blocked in ensureCapture(), so B gives no frame and B does not run its runSynchronously tasks. After a 3 s cooldown A takes the lock again for 50 s. In the base version an attempt had no first-frame wait, so A 'opened' at once and B was not delayed. If the reopen fix of the first finding is applied, each reopen of B is delayed in the same way.
- Evidence: ensureCapture() lines 127-166: the loops over getIoModeCandidates(), buildCandidates(ioMode) and attempts, the call openCandidate(candidate) and sleepQuietly(250L * attempt) are all inside 'synchronized (CAPTURE_OPEN_LOCK)'. openCandidate() lines 197-208 waits up to 2500 ms for the first frame. A candidate that reached PLAYING but gave no frame is tried again openAttempts times, although the retry was made for open failures.
- Method from the review (use it unless the "Decisions" section above says something different): File GStreamerUSBFrameProvider.java, ensureCapture() and openCandidate(). Hold CAPTURE_OPEN_LOCK only for staggerOpenIfRequested(), GStreamerCapture.open(candidate.pipeline(), candidate.outputMode()) and the write of lastOpenCompleteMillis (write it when open() returns a capture). Move the first-frame wait (the grab loop of openCandidate), releaseCapture() and the sleepQuietly() between attempts out of the synchronized block. Change the retry rule: if open() fails, try again up to openAttempts times (as now); if open() is successful but no frame comes before the timeout, release the capture and go to the next candidate without a second attempt of the same pipeline. Then the lock is held for one native create call at most, and a full cycle of a silent camera is 6 x 2.5 s outside the lock. Test (native library and elements available, candidate list injectable): provider A uses a pipeline that reaches PLAYING and gives no buffer ('appsrc is-live=true ! video/x-raw,format=GRAY8,width=64,height=48,framerate=30/1 ! appsink name=pvappsink'), provider B uses 'videotestsrc is-live=true ! video/x-raw,format=GRAY8,width=64,height=48,framerate=30/1 ! appsink name=pvappsink'. Start a thread that calls A.get(), wait 300 ms, then call B.get() in a loop on the test thread and assert that B gives a non-empty frame in less than 1.5 s. Before the fix this takes longer than the full cycle of A.

### D2: A camera that stops giving frames is never opened again, and after end-of-stream the vision thread runs in a tight loop (same behavior in base 412ccea)
- Location: photon-core/src/main/java/org/photonvision/vision/frame/provider/GStreamerUSBFrameProvider.java:85
- Failure scenario: Two cameras on one coprocessor. Camera A has a short USB disconnect (cable, EMI, brown-out). v4l2src posts an error and GstBaseSrc pushes EOS to the appsink. (1) The capture stays 'open' for Java, so camera A gives no frame until PhotonVision is restarted. (2) After EOS the native grab() returns at once (worker path: workerEnded makes the wait predicate true; raw path: gst_app_sink_try_pull_sample returns NULL at once at EOS). Java returns an empty frame with no sleep, so VisionRunner.update() loops as fast as it can: each loop makes several Mat objects and sends a blank CVPipelineResult to the result consumers (NetworkTables, UI). One of the 4 CPUs of the taskset is used fully and the garbage collector gets a high load, which decreases the frame rate of the good camera B.
- Evidence: ensureCapture() line 123: 'if (capture != null && capture.isOpen()) return true;' and GStreamerCapture.isOpen() is only 'nativePtr != 0'. grabGStreamerFrame() lines 85-88: 'if (frame == null) return new CapturedFrame(new CVMat(), ...)' with no sleep, no counter and no releaseCapture(). Native GStreamerCaptureJNI.cpp line 1795: ready = latest != nullptr || workerEnded; line 1506: the worker ends on gst_app_sink_is_eos. VisionRunner.update() lines 259-264 has no sleep in the empty-frame branch. The base version has the same Java lines, so this is not a regression, but it is a real loss of one camera in a match.
- Method from the review (use it unless the "Decisions" section above says something different): File GStreamerUSBFrameProvider.java. Add a field 'long lastFrameNanos' and a constant STALL_REOPEN_NANOS from env PV_USB_GSTREAMER_STALL_REOPEN_MS (default 2000, 0 = off). In ensureCapture(), set lastFrameNanos = System.nanoTime() when a candidate opens. In grabGStreamerFrame(): record grabStart = System.nanoTime() before capture.grab(250). If the frame is not null, set lastFrameNanos = System.nanoTime(). If the frame is null: (a) if STALL_REOPEN_NANOS > 0 and now - lastFrameNanos >= STALL_REOPEN_NANOS, write a warning, call releaseCapture(), set captureFailed = true and lastOpenFailureMillis = System.currentTimeMillis(); the existing cooldown and candidate logic then opens the camera again. (b) else if now - grabStart is less than 20 ms (the native side returned at once), call sleepQuietly(20). Then return the empty CapturedFrame as now. Apply the fix of the open-lock finding together with this one, because a reopen needs CAPTURE_OPEN_LOCK. Note for the zero-copy raw path: frames that the pipeline still holds keep GstSample references when the capture is closed; the default MJPEG path has no such references. Test: make the candidate list injectable (package-private overridable method or constructor argument). With the native library available (assumeTrue), use the pipeline 'videotestsrc is-live=true num-buffers=15 ! video/x-raw,format=GRAY8,width=64,height=48,framerate=30/1 ! appsink name=pvappsink'. Read frames until they stop. Then call get() for 500 ms and assert that the number of calls is small (for example less than 40; before the fix it is many thousands). Then, with a short stall time and cooldown set for the test, assert that get() gives a non-empty frame again.

### D3: A frame is not released when the pipeline changes while the vision thread gets the frame (same code in base 412ccea)
- Location: photon-core/src/main/java/org/photonvision/vision/processes/VisionRunner.java:265
- Failure scenario: Robot code changes the pipeline index or the driver mode through NetworkTables. NTDataPublisher calls VisionModule.setPipeline() on the NetworkTables thread, and that calls pipelineManager.setIndex() at once. The vision thread is in frameSupplier.get() most of the time (it waits for the next camera frame), so the change frequently occurs between line 219 and line 265. Then 'pipeline == pipelineSupplier.get()' is false, the if/else-if chain has no branch for the frame, and the frame is dropped without release(). With the GStreamer provider each such frame keeps a native FrameHolder: a 2.1 MB pooled gray buffer (1600x1304) on the MJPEG path, or a GstSample (camera or converter buffer) on the zero-copy raw path, where some tens of leaked camera buffers can stop the capture. The CVMat tracker also writes 'finalized without release' errors.
- Evidence: VisionRunner.update() lines 259-320: 'if (both images empty) { frame.release(); ... } else if (pipeline == pipelineSupplier.get()) { ... }' and no else branch. The comment at line 274 says the frame is scrapped in this case, but no code releases it. GStreamerFrame.toCVMat() releases the native holder only through CVMat.release().
- Method from the review (use it unless the "Decisions" section above says something different): File VisionRunner.java, method update(): add 'else { frame.release(); }' after the 'else if (pipeline == pipelineSupplier.get()) { ... }' block. Test: a unit test with a fake FrameProvider whose get() returns a Frame with CVMat objects that count their release callbacks, and a pipelineSupplier that returns pipeline P1 on the first call of a loop and pipeline P2 on the second call. Run some loops and assert that the release counter is equal to the number of frames that were given and that no pipeline got these frames.

### D4: With a 1-channel camera image the processed image is an alias of the input image, so the output stream drawing changes the input image: an input snapshot contains the overlays
- Location: photon-core/src/main/java/org/photonvision/vision/frame/provider/CpuImageProcessor.java:92
- Failure scenario: Script default PV_USB_GSTREAMER_CPU_FORMAT=GRAY8, AprilTag pipeline, only the output (processed) stream is shown, so m_copyInput is false. CpuImageProcessor.get() makes processedImage as 'new CVMat(input.colorImage.getMat(), null, false)': the same Java Mat object as colorImage. In VisionModule.StreamRunnable, OutputStreamPipeline.process() resizes this Mat, converts it to BGR in place (OutputMatPipe) and draws the ML boxes and the tag overlays on it. Then consumeResults() calls inputFrameSaver.accept(frame.colorImage). If the user or the robot code asks for an input snapshot at that time, the saved 'input' picture is the resized output picture with the overlays, not the camera image. With the old default (BGR) the two Mats were different and the input snapshot was clean. Also, if the input stream demand starts between the VisionRunner loop and the stream thread, the alias Mat is resized two times and both streams show the same picture for some frames. The tag data is not affected, because the pipeline has completed the frame before the stream thread gets it.
- Evidence: CpuImageProcessor.java lines 92-93 (alias when channels() == 1 && !m_copyInput; the code is from base, but the GRAY8 default of the two run scripts makes it the normal path). OutputStreamPipeline.java lines 141-142 (inMat and outMat from the two CVMats), 156, 165, 213-228 (in-place resize, GRAY2BGR and drawing on outMat). VisionModule.java lines 320-321 and 800 (inputFrameSaver.accept(frame.colorImage) after the stream pipeline).
- Method from the review (use it unless the "Decisions" section above says something different): File CpuImageProcessor.java, method get(): use the alias only when no stream needs the frame: change the condition to 'input.colorImage.getMat().channels() == 1 && !m_copyInput && !m_copyOutput'. In all other cases use the existing branch (m_outputMatPool.take() and m_grayPipe.processInto, which makes a copy for a 1-channel input). m_copyOutput is already set by requestFrameCopies(effectiveInput, effectiveOutput). The benchmark and the simulation use requestFrameCopies(false, false), so their path does not change. Test: a small CpuImageProcessor subclass that returns a 1-channel Mat. Case 1: requestFrameThresholdType(GREYSCALE), requestFrameCopies(false, true): assert that frame.processedImage.getMat().dataAddr() is different from frame.colorImage.getMat().dataAddr(); run OutputStreamPipeline.process with AprilTagPipelineSettings and StreamDemand(false, true) and assert that colorImage still has 1 channel, the same size and the same bytes. Case 2: requestFrameCopies(false, false): assert that the two dataAddr values are equal (zero-copy path stays).

### D5: Orange Pi run script: defaults that depend on HOME stop the start or silently give no camera when the script runs as root (which the real-time priority needs); a capture library that is not loaded gives no clear error
- Location: tools/orangepi5-run-photonvision-mltag-gstreamer.sh:17
- Failure scenario: The script says that PV_GSTREAMER_CAPTURE_RT_PRIORITY needs root or CAP_SYS_NICE. (1) As a systemd service without User=, HOME is not set: with 'set -u' line 17 stops with 'HOME: unbound variable'. (2) With sudo, HOME is /root: 'cd /root/photonvision' fails and the script stops. If the user then sets PV_ORANGEPI_HOME only, PV_GSTREAMER_CAPTURE_JNI_LIB still points to /root/pv-gstreamer-capture-jni/build/libpv_gstreamer_capture_jni.so, which does not exist. GStreamerCaptureJNI.load() catches the UnsatisfiedLinkError and returns false with no log line, GStreamerCapture.open() returns null, and the provider writes only 'Failed to open native GStreamer USB capture pipeline; will retry' again and again. PhotonVision runs with no camera and the log does not give the cause. (3) 'exec taskset -c 4-7 java ...' has no fallback: if the kernel refuses the CPU list (CPUs 4-7 not online, cpuset of a container) taskset stops with 'Invalid argument' and PhotonVision does not start. The Rubik script has the same points (2) with fixed /home/photon paths and (3).
- Evidence: orangepi5 script lines 17 and 19 ($HOME in the cd target and in the library path, under 'set -euo pipefail'), lines 124-127 (exec taskset with no check). GStreamerCaptureJNI.java lines 53-65 (load() returns false with no message). GStreamerCapture.open() lines 86-88 (returns null if the library is not available). GStreamerUSBFrameProvider.ensureCapture() lines 147-170 (only general warnings).
- Method from the review (use it unless the "Decisions" section above says something different): Scripts (both run scripts): after the export of PV_GSTREAMER_CAPTURE_JNI_LIB add a check: if the file is not readable, print 'Capture library not found: <path>. Build it (see the top of this script) or set PV_GSTREAMER_CAPTURE_JNI_LIB.' to stderr and exit 1. In the Orange Pi script use "${HOME:-/root}" or give a clear message when HOME is not set, and print the directory when cd fails. Before the exec, test the CPU list: if 'taskset -c "$cpu_affinity" true' fails, print a warning and start java without taskset. Java: in GStreamerCaptureJNI.load() keep the message of the caught error in a static field and write it one time with the logger; in GStreamerUSBFrameProvider.ensureCapture(), if GStreamerCapture.isAvailable() is false, write one error line with the library path and the load error, set captureFailed and return false without the candidate loop. Test: run each script with PV_GSTREAMER_CAPTURE_JNI_LIB set to a path that does not exist and with PV_PHOTONVISION_JAR set to a dummy, and assert exit code 1 and the message; run with PV_CPU_AFFINITY=999 and a stub 'java' first in PATH and assert that the stub is started; a unit test that asserts that ensureCapture() returns false at once and writes the library message when the library is not loaded.
