## Decisions of the lead engineer
- Implement items C1 to C3 below, in this order. They are the methods of an independent review; the review text for each item follows.
- C1 (JPEG warnings): a real camera can send frames with padding bytes or harmless header warnings. Such frames must be delivered, pixel-exact. Only frames with damaged picture data are rejected. Use the method of the review.
- C2 (zero-copy): give Java a Mat that points into GStreamer memory only in the case that the base code had (interleaved format, system memory, not read-only). All other raw frames (a raw GRAY8 camera, luma plane of a decoder, packed luma) are copied into a pooled buffer and the GStreamer buffer is released immediately. This is also necessary because the pipeline can keep 1 to 4 frames in work: a frame must not keep a camera buffer of v4l2src. Tiled formats are not supported. Use the method of the review item C2. (A second review proposed a read-write map for the same fault. Do NOT use that method.)
- C3 (real-time priority): restore the thread policy when the GStreamer streaming thread leaves, as in the review text. If the test cannot get SCHED_FIFO in this environment it must skip with assumeTrue; in this container the process is root and SCHED_FIFO is permitted.
- After the changes: build both variants of the library, then run `--tests "*GStreamerCaptureTest" --tests "*GStreamerPipelineCandidatesTest"` with PV_GSTREAMER_CAPTURE_JNI_LIB set. All tests must pass. Run GStreamerCaptureTest a second time with `PV_GSTREAMER_CAPTURE_WRAP_BUFFER=true` in the environment too.

## Items (review text)
### C1: JPEG warning classification drops good frames: intermittent padding is never tolerated, and harmless header warnings reject each frame
- Location: tools/jetson-gstreamer-capture-jni/src/GStreamerCaptureJNI.cpp:1196
- Failure scenario: Scenario 1 (silent frame loss): a UVC camera adds some padding bytes before the EOI marker. libjpeg reports JWRN_EXTRANEOUS_DATA only on a part of the frames, because the bit reader reads ahead and frequently takes the padding without a warning. Each frame that has the warning is dropped (corruptFrames++). A frame without the warning sets consecutiveExtraneousOnly back to 0, so the limit of 30 consecutive frames is almost never reached and the tolerance never starts. The first-frame check in openCandidate passes with a clean frame, so there is no fallback to the legacy pipeline. Result: the direct MJPEG mode delivers only a part of the camera frames for an unlimited time, with no log line. The base pipeline (jpegdec) delivered all these frames. Scenario 2 (no frame at all): a camera whose frames always give a harmless warning (JWRN_NOT_SEQUENTIAL: zero bytes in the SOS parameters, JWRN_JFIF_MAJOR, JWRN_ADOBE_XFORM, or JWRN_JPEG_EOF alone because the EOI marker is missing). jpegEmitMessage sets dataDamaged for each warning that is not JWRN_EXTRANEOUS_DATA, so each frame is rejected. With PV_USB_GSTREAMER_CAPTURE_MODE=direct there is never a frame. With auto, each io-mode spends 3 attempts of 2.5 s and then uses the legacy pipeline, so the direct mode that the FPS estimate depends on is not active.
- Evidence: jpegEmitMessage (lines 1196-1207): only JWRN_EXTRANEOUS_DATA sets extraneousBytes; each other warning code sets dataDamaged. frameFromJpegSample (lines 1393-1414): an extraneous-only frame is accepted only if tolerateExtraneousJpegBytes is set or ++consecutiveExtraneousOnly >= 30; the else branch of 'result == Damaged' sets consecutiveExtraneousOnly = 0 on each clean frame; a frame that is not accepted is released and corruptFrames is incremented. libjpeg (jdhuff.c start_pass_huff_decoder) makes JWRN_NOT_SEQUENTIAL a warning because the pixels are decoded completely. Truncated entropy data always gives JWRN_HIT_MARKER in addition to JWRN_JPEG_EOF, so JWRN_JPEG_EOF alone means only that the EOI marker is missing. The run scripts do not set PV_GSTREAMER_CAPTURE_ALLOW_JPEG_EXTRA_BYTES. I did not measure which warnings the owner's cameras give; the fault is the logic.
- Method from the review (use it unless the "Decisions" section above says something different): File GStreamerCaptureJNI.cpp. (1) JpegErrorManager: keep dataDamaged (fatal). Add prematureEof (bool), extraneousBytesTotal (unsigned), extraneousOnlyBeforeEoi (bool, start true). (2) jpegEmitMessage, for level < 0, switch on cinfo->err->msg_code: JWRN_EXTRANEOUS_DATA: add msg_parm.i[0] to extraneousBytesTotal, and if msg_parm.i[1] != 0xD9 set extraneousOnlyBeforeEoi = false. JWRN_JPEG_EOF: prematureEof = true. JWRN_NOT_SEQUENTIAL, JWRN_JFIF_MAJOR, JWRN_ADOBE_XFORM: record nothing (harmless). Default (JWRN_HIT_MARKER, JWRN_HUFF_BAD_CODE, JWRN_MUST_RESYNC, JWRN_BOGUS_PROGRESSION, JWRN_TOO_MUCH_DATA, unknown codes): dataDamaged = true. Reset all fields at the start of decodeJpeg. (3) decodeJpeg result: Damaged if dataDamaged. New value Suspect if not dataDamaged and (extraneousBytesTotal > 0 or prematureEof). Ok in all other cases. The test-only extra decode must continue to ignore these fields (copy the fields of the first decode before the extra-decode loop, as extraneousOnly is copied now). (4) frameFromJpegSample: Damaged = reject as now. Suspect: accept immediately if capture->tolerateExtraneousJpegBytes is set, or if prematureEof is false and extraneousOnlyBeforeEoi is true and extraneousBytesTotal <= 16 (alignment padding, all MCUs were decoded). For other Suspect frames replace consecutiveExtraneousOnly with a window count that a clean frame does not reset: count each decoded frame in windowFrames and each Suspect frame in windowSuspect; when windowSuspect >= 30 set tolerateExtraneousJpegBytes = true and print the current log line once; when windowFrames reaches 600 without that, set both counts to 0. A Suspect frame that is not accepted is dropped as now. Tests in GStreamerCaptureTest with multifilesrc, expected pixels from Imgcodecs.imread of the original file: (a) 12 zero bytes inserted before the last FF D9: the first delivered frame is pixel-exact and corruptFrames == 0. (b) two files that alternate (multifilesrc start-index=0 stop-index=1 loop=true): one clean, one with 64 zero bytes before EOI: after 400 delivered frames corruptFrames <= 40 and both pictures are delivered pixel-exact. (c) the Se byte of the SOS header changed from 0x3F to 0x00: frames are delivered from the first grab, pixel-exact, corruptFrames == 0. (d) the last two bytes (FF D9) removed: frames are delivered after not more than 100 pulled samples, pixel-exact. (e) the existing damagedJpegIsNotDelivered test (file cut at 60%) must still give no frame.

### C2: Zero-copy Mat on a read-only GStreamer mapping: an in-place write from Java stops the JVM with SIGSEGV (hardware JPEG decoder or dmabuf camera buffers)
- Location: tools/jetson-gstreamer-capture-jni/src/GStreamerCaptureJNI.cpp:1083
- Failure scenario: Orange Pi run script defaults (PV_GSTREAMER_CAPTURE_WRAP_BUFFER=true, PV_USB_GSTREAMER_CPU_FORMAT=GRAY8) with the documented option PV_USB_GSTREAMER_HW_JPEG_DECODER=mppjpegdec. The candidate is 'v4l2src ! queue ! mppjpegdec ! appsink' with no converter. frameFromRawSample classifies NV12/NV16 as LumaPlane and, because wrap is on, gives Java a cv::Mat that points directly into plane 0 of the decoder buffer. The buffer is mapped with GST_MAP_READ only. For fd-backed (dmabuf) memory GStreamer does mmap with PROT_READ for a read map. When the camera rotation is 180 degrees, CpuImageProcessor.get() calls RotateImagePipe, which does Core.rotate(in, in, ROTATE_180) in place, on each frame: a write to a PROT_READ page, SIGSEGV, PhotonVision stops. The same occurs when the stream thread draws on the input image (OutputStreamPipeline: draw2dCrosshairPipe.run(Pair.of(inMat, ...)) for the non-ML AprilTag pipeline). The same hazard exists for a raw GRAY8 camera in direct mode with io-mode=4 (dmabuf). The base code wrapped only buffers that came from videoconvert/nvvidconv (system memory), so the base did not have this crash.
- Evidence: GStreamerCaptureJNI.cpp line 1083: mustCopy = format.layout == RawLayout::PackedLuma || !capture->wrapMappedBuffer; so Interleaved and LumaPlane are wrapped (lines 1084-1090) for any memory type. Line 1060: gst_video_frame_map(..., GST_MAP_READ). GStreamerUSBFrameProvider.buildCandidates line 309: tail = gray ? "" : " ! videoconvert ..." (decoder output goes directly to the appsink) and lines 324-336 (direct raw GRAY8 candidate). tools/orangepi5-run-photonvision-mltag-gstreamer.sh lines 20, 53, 60-62. RotateImagePipe.process: Core.rotate(in, in, ...). CpuImageProcessor.get(): m_rImagePipe.run(input.colorImage.getMat()). OutputStreamPipeline line 171. I did not run mppjpegdec here; that its buffers are dmabuf memory is from the Rockchip plugin design, and the PROT_READ mapping is from gstfdmemory.c (prot is PROT_READ unless GST_MAP_WRITE is requested).
- Method from the review (use it unless the "Decisions" section above says something different): File GStreamerCaptureJNI.cpp, function frameFromRawSample. Wrap without a copy only in the case that the base code had: wrapAllowed = capture->wrapMappedBuffer && format.layout == RawLayout::Interleaved && each GstMemory of holder->buffer (gst_buffer_n_memory / gst_buffer_peek_memory) is system memory (gst_memory_is_type(mem, GST_ALLOCATOR_SYSMEM)) and is not GST_MEMORY_IS_READONLY. Set mustCopy = !wrapAllowed. All other cases (LumaPlane, PackedLuma, camera buffers, decoder buffers) use the existing copy into a pooled buffer; copyPlane already copies only plane 0, and the GStreamer buffer is then released immediately. Cost: one copy of width x height bytes for each frame (about 2 MB at 1600x1304) in the hardware-decoder mode only; the software MJPEG mode is not changed. In the same change, make classifyRawFormat return Unsupported when GST_VIDEO_FORMAT_INFO_IS_TILED(finfo) is true: a tiled NV12 format passes the current checks, but its stride value is a tile count, so copyPlane would read outside the buffer. Proof by test (GStreamerCaptureTest, run with PV_GSTREAMER_CAPTURE_WRAP_BUFFER=true in the environment): (a) 'videotestsrc ! video/x-raw,format=NV12,width=326,height=242 ! appsink': grab a frame, call mat.setTo(new Scalar(0)) on it, then grab 5 more frames; no crash, and getStats().convertNanosSum() > 0 (a copy was made). (b) the legacy shape '... ! videoconvert ! video/x-raw,format=BGR ! appsink': convertNanosSum() == 0 (still zero-copy, as in the base). (c) rawFormatsGiveTheExactLumaBytes and decoderOutputPlaneIsUsedAsGrayImage must pass with and without the environment variable.

### C3: Real-time priority stays on a pooled GStreamer thread after the capture is closed, and a later task (for example the legacy software decode) can run at SCHED_FIFO
- Location: tools/jetson-gstreamer-capture-jni/src/GStreamerCaptureJNI.cpp:588
- Failure scenario: PV_GSTREAMER_CAPTURE_RT_PRIORITY=10 (the default of both run scripts) and the process is permitted to use SCHED_FIFO. The direct candidate reaches PLAYING and its source thread pushes one buffer or more (the probe sets SCHED_FIFO on that thread), but no frame is accepted in 2.5 s (for example scenario 2 of the JPEG warning finding). releaseCapture() stops the pipeline. The streaming thread is not destroyed: GStreamer tasks run on threads of a shared GLib thread pool, and a thread that has no task waits for a new task (0.5 s in the same pool, then up to 15 s in the global list of unused threads). The provider opens the legacy candidate 250 ms later. Its queue task (jpegparse + jpegdec + videoconvert for each 2 MP frame) can get the old thread, which still has SCHED_FIFO 10. Then an unlimited software decode runs at real-time priority for the remaining run time, against the statement in the code that the real-time threads do a limited amount of work. The normal vision threads on that CPU run only when this thread waits. The 'static thread_local priorityApplied' flag also stays true on the reused thread. The tag data is not changed; the effect is on the frame timing of the other threads.
- Evidence: sourceBufferProbe lines 587-592 call applyRealtimePriorityToCurrentThread() (lines 236-251: pthread_setschedparam(pthread_self(), SCHED_FIFO, ...)) on the GStreamer streaming thread. No code sets the policy back: destroyCapture (lines 522-571) only removes the probe and stops the pipeline. GStreamerUSBFrameProvider.ensureCapture/openCandidate close a failed candidate and open the next one after sleepQuietly(250L * attempt). The JPEG decode thread is a std::thread that ends in stopWorker, so it does not have this fault. The thread reuse is the documented behavior of non-exclusive GThreadPool pools, which GstTaskPool uses; I did not run it here because process and build commands were not permitted.
- Method from the review (use it unless the "Decisions" section above says something different): File GStreamerCaptureJNI.cpp. (1) In applyRealtimePriorityToCurrentThread, before the change, read the current policy and parameter with pthread_getschedparam and keep them in thread_local variables together with a thread_local flag 'promoted'. (2) In createCapture, after the pipeline is made and before PLAYING, install a bus sync handler: gst_bus_set_sync_handler(bus, handler, nullptr, nullptr). The handler returns GST_BUS_PASS for each message, so logBusFailure continues to work. For GST_MESSAGE_STREAM_STATUS it calls gst_message_parse_stream_status; when the type is GST_STREAM_STATUS_TYPE_LEAVE and the thread_local flag 'promoted' is set, it restores the saved policy and parameter with pthread_setschedparam(pthread_self(), ...) and clears 'promoted' and 'priorityApplied'. GStreamer posts the LEAVE message from the streaming thread itself when its task ends (during PAUSED to READY, before the bus is set to flushing), and a sync handler runs on the posting thread, so the restore runs on the correct thread. (3) Keep the probe code that sets the priority. Proof by test (Linux, skip with assumeTrue when no thread got SCHED_FIFO because the permission is missing): with PV_GSTREAMER_CAPTURE_RT_PRIORITY=10, open 'videotestsrc is-live=true ! jpegenc ! appsink', grab 10 frames, and read field 41 (policy) of each /proc/self/task/<tid>/stat: one thread or more has policy 1. Close the capture, wait 200 ms, read again: no thread has policy 1. Then open a legacy-shape pipeline with a queue and check that only one thread (the source thread) has policy 1.
