# Specification B: InferenceOverlapController

Files:

How the pipeline uses the controller (AprilTagPipeline.processWithInferenceLanes): for each camera frame it calls onFrame(now, frameTimestamp, pendingFrames, inferenceAverage, inferenceSamples).
- SKIP_INPUT (only when frames are in work): the input frame is released, the result of the oldest frame in work is returned.
- DEFER: the input frame is started and stays in work, the call returns no result.
- COMPLETE_OLDEST: the input frame is started, the result of the oldest frame in work is returned (in SERIAL mode that is the input frame).
Then it calls onCallEnd(now, postInferenceNanos) (or -1 for a call with no result).

### B1: A partial STALE discard resets the controller while frames stay in work: each later result is one or two calls old, with no recovery
- Location: /home/user/photonvision-mltag/photon-core/src/main/java/org/photonvision/vision/pipeline/AprilTagPipeline.java:441
- Failure scenario: OVERLAP with depth 3 (22 ms inference + 8 ms decode, 60 FPS camera). Robot code sets the NetworkTables FPS limit to 5 (VisionRunner.waitUntilNextTick, one pipeline call each 200 ms), so the frame timestamps are about 200 ms apart. At the fourth slow call the deque is [D, E, F] with ages 583 ms, 400 ms, 200 ms. discardStalePendingFrames removes only D (more than 500 ms), keeps E and F, and then calls overlapController.reset(). The controller is now SERIAL but the deque has 2 frames. onFrame returns COMPLETE_OLDEST, the pipeline adds the input frame and returns the oldest frame. The deque stays at 2 for all later calls: each published result is for the frame of two calls before (400 ms older than necessary, about 600 ms after capture instead of about 230 ms), although the work for a frame takes 30 ms. The idle time is 200 ms, so the controller never starts OVERLAP and never drains. With FPS limit 3 one frame stays (333 ms older). With depth 2 and FPS limit 3 the result is the same. A single camera stall of 467 ms to 500 ms at depth 3 gives the same state at 60 FPS: the log says 'one frame at a time', getDepth() is 0, but 1 or 2 frames stay in work until the next settings change or a pause of more than 500 ms. The timestamps of the results are correct, but the results are older than necessary and the state does not go back.
- Evidence: AprilTagPipeline.java lines 443-454: the while loop stops at the first frame that is not stale, then `if (discarded && overlapController != null) overlapController.reset();` runs while pendingFrames is not empty. InferenceOverlapController.java lines 171-217: the `!overlap` branch has no path to SKIP_INPUT, and line 214 `if (overlap && pendingFrames < depth) return DEFER; return COMPLETE_OLDEST;` gives COMPLETE_OLDEST for SERIAL with pendingFrames > 0. A new start of OVERLAP (line 183-184) sets depth = 1 and ignores pendingFrames. No test uses a controller reset with frames in work.
- Method from the review (use it unless the "Decisions" section above says something different): Two changes. (1) AprilTagPipeline.discardStalePendingFrames(long): replace the while loop. New logic: if pendingFrames is empty, return. If `newestTimestampNanos - pendingFrames.peekFirst().frame().timestampNanos > STALE_PENDING_NANOS`: write the warning one time and call discardPendingFrames() (it waits for ALL frames in work, releases them and resets the controller). Then a controller reset always has an empty deque, and the new frame is completed immediately. (2) InferenceOverlapController.onFrame, last lines: replace `if (overlap && pendingFrames < depth) return Action.DEFER; return Action.COMPLETE_OLDEST;` with `int wanted = overlap ? depth : 0; if (pendingFrames > wanted) return Action.SKIP_INPUT; if (pendingFrames < wanted) return Action.DEFER; return Action.COMPLETE_OLDEST;`. This brings the number of frames in work back to the controller state from each possible state. The SKIP_INPUT code in the pipeline needs no change. Tests: (a) InferenceOverlapControllerTest: `new InferenceOverlapController(2)`; onFrame(now, ts, pendingFrames=2, 20 ms, 100) must give SKIP_INPUT, with pendingFrames=1 SKIP_INPUT, with 0 COMPLETE_OLDEST. (b) AprilTagPipelineInferenceLanesTest: SimulatedModel(30), 2 lanes; run at 60 FPS until a result is not for its own input frame (overlap is active); then make 12 calls with Thread.sleep(20) between them and frame timestamps that increase by 200 ms for each call; assert that from the 5th of these calls each call returns a result whose inputAndOutputFrame is the input frame of that call; after pipeline.release() assert colorImage.isReleased() for each frame. Before the fix the results stay two calls old.

### B2: The overlap depth only increases: one short work peak adds one camera frame period of latency for the remaining run time
- Location: /home/user/photonvision-mltag/photon-core/src/main/java/org/photonvision/vision/pipeline/InferenceOverlapController.java:224
- Failure scenario: 60 FPS camera, 22 ms inference + 4 ms decode = 26 ms: depth 2 (limit for depth 3 is 1.7 x 16.67 = 28.3 ms). One frame has a post-inference time of 100 ms (garbage collection, a large near tag, CPU stall). postInferenceAverage goes from 4 ms to 13.6 ms and then decreases by 10% for each call: workNanos is 35.6, 34.6, 33.8, 33.0, 32.3, 31.7, 31.1, 30.6 ms for the next 8 calls. All 8 are above 28.3 ms, so moreDepthStreak gets to CALLS_TO_ADD_DEPTH and depth becomes 3. The work goes back to 26 ms, but the depth stays 3: each result is published 16.7 ms later than necessary until a settings change or a pause of more than 500 ms. Each single post-inference sample above about 53 ms does this. The same occurs for depth 3 to 4 (a stall of about 320 ms, or a time with large tags), and when the camera frame rate decreases in OVERLAP (for example 60 to 30 FPS with 30 ms of work: the depth stays 3, the latency becomes 3 x 33 ms = 100 ms, the rule itself asks for depth 2).
- Evidence: updateDepth (lines 224-237) has only `depth++`. depth is set to a smaller value only in reset() (line 261) and when OVERLAP starts again (line 184). OVERLAP stops only when workNanos < 0.9 x cameraPeriod (lines 197-200), which is never true for a 22 ms inference at 60 FPS. The EMA in onCallEnd (lines 249-252) has a weight of 0.1, so one sample of 100 ms keeps workNanos above the limit for 8 calls.
- Method from the review (use it unless the "Decisions" section above says something different): InferenceOverlapController: add `static final int CALLS_TO_REMOVE_DEPTH = 600;` (10 s at 60 FPS), `static final double DEPTH_DOWN_MARGIN = 0.1;` and a field `int lessDepthStreak`. In updateDepth: keep the increase rule, but do not let the early return for `depth >= MAX_DEPTH` skip the new rule (only `cameraPeriod <= 0` returns early). New rule after the increase rule: `boolean lessDepthSufficient = depth > 1 && workNanos < (depth - 1 - reserve - DEPTH_DOWN_MARGIN) * cameraPeriod; lessDepthStreak = lessDepthSufficient ? lessDepthStreak + 1 : 0; if (lessDepthStreak >= CALLS_TO_REMOVE_DEPTH) { depth--; lessDepthStreak = 0; moreDepthStreak = 0; }`. Set lessDepthStreak = 0 in reset() and when OVERLAP starts. The frame is removed by the final decision of the first finding (`pendingFrames > depth` gives SKIP_INPUT): one camera frame is skipped for each step down. The down limit is 0.1 period below the up limit `(depth - 1 - reserve)` of the smaller depth, and 600 calls in sequence are necessary, so the depth cannot go up and down quickly. Tests in InferenceOverlapControllerTest with the Simulation class: (a) Simulation(2, 16_666_667, 22 ms, 3 ms): run(120), assert depth 2; set postInference = 60 ms for 3 steps, then 3 ms again; run(120), assert depth 3 (this shows the cause); run(1200), assert depth 2 and that `skipped` increased by exactly 1; a subsequent run(600) gives 60 FPS +/- 0.5 and `deferred` and `skipped` do not change. (b) Simulation(2, 16_666_667, 24 ms, 8 ms): run(120), assert depth 3; set cameraPeriod = 33_333_333 and lastFrameIndex = now / cameraPeriod; run(1500); assert overlap is active and depth is 2.

### B3: The depth increases when a stage is the limit (work thread or lanes): more latency, the same result rate
- Location: /home/user/photonvision-mltag/photon-core/src/main/java/org/photonvision/vision/pipeline/InferenceOverlapController.java:231
- Failure scenario: Two lanes, 60 FPS camera, 26 ms inference, 20 ms tag decode and pose (near or many tags, or CPU load from the second camera). The work thread can give one result each 20 ms (50 FPS) with any depth of 2 or more. The vision thread waits in awaitResult for each result, so the time from the start of a frame to its result is (depth + 1) x 20 ms. The camera period estimate stays 16.67 ms (80% of the frame times are one period). workNanos = 46 ms is more than (3 - 0.3) x 16.67 = 45.0 ms, so the depth goes to MAX_DEPTH = 4: 100 ms for each frame instead of 60 ms with depth 2, at the same 50 FPS. With the numbers of the test depthDoesNotIncreaseWhenTheWorkThreadIsTheLimit (22 ms + 20 ms) the depth becomes 3 (80 ms) and depth 2 gives the same 50 FPS (60 ms); the test accepts `<= 3` and passes only because 42 ms is below 45 ms. The same occurs when the lanes are the limit (2 lanes, 40 ms inference, 2 ms decode: 50 FPS with depth 2 and with depth 3, the controller selects 3). Together with the second finding this latency stays after the overload ends.
- Evidence: updateDepth line 231: `moreDepthNecessary = workNanos > (depth - reserve) * cameraPeriod` uses only the sum of the stage times. It does not look at the rate limit of a stage: the single work thread gives at most 1 / postInferenceAverage results, the lanes give at most lanes / inferenceAverage. Derivation for a saturated work thread: result time T(k) = max(S(k) + inference, T(k-1)) + post, with frame start S(k) = T(k-1-depth); the period is `post` as soon as depth x post >= inference, so depth = lanes is sufficient and more depth only adds one stage period of latency for each step. The field `lanes` is used only for the `lanes <= 1` test (line 153).
- Method from the review (use it unless the "Decisions" section above says something different): InferenceOverlapController.updateDepth: add the parameter inferenceAverageNanos (pass it from onFrame) and a field `boolean stageIsLimit`. After the `cameraPeriod <= 0` test: `double stagePeriod = Math.max(inferenceAverageNanos / lanes, postInferenceAverage); if (stagePeriod >= cameraPeriod) stageIsLimit = true; else if (stagePeriod < 0.9 * cameraPeriod) stageIsLimit = false; int depthLimit = stageIsLimit ? Math.min(MAX_DEPTH, lanes) : MAX_DEPTH;`. Use `depth >= depthLimit` instead of `depth >= MAX_DEPTH` to stop the increase. Add a streak `aboveLimitStreak`: if depth > depthLimit for CALLS_TO_STOP_OVERLAP (60) calls in sequence, then depth-- (the frame is removed by the `pendingFrames > depth` gives SKIP_INPUT decision of the first finding). Reset stageIsLimit and the streak in reset() and when OVERLAP starts. Tests in InferenceOverlapControllerTest: (a) Simulation(2, 16_666_667, 26 ms, 20 ms): run(600), assert getDepth() == 2 (before the fix: 4); the next run(600) gives 50 FPS +/- 1. (b) Change the limit in depthDoesNotIncreaseWhenTheWorkThreadIsTheLimit from `<= 3` to `== 2`, the rate assertion stays 50 +/- 1. (c) Simulation(2, 16_666_667, 40 ms, 2 ms): run(600), assert depth == 2 and a rate of 50 FPS +/- 1. The tests threeLanesServeAVerySlowModel (40 ms < 3 x 16.67 ms) and slowInferenceStartsOverlapAndReachesTheCameraRate must stay unchanged with depth 3.

- Method from the review (use it unless the "Decisions" section above says something different): InferenceOverlapController.onFrame, OVERLAP branch, before the serialSufficientStreak logic: add `static final int CALLS_TO_STOP_OVERLAP_ON_LONG_IDLE = 4;` and a field `int longIdleStreak`. `boolean longIdle = idleNanos > 0 && inferenceSamples > 0 && workNanos > 0 && idleNanos > 1.5 * workNanos; longIdleStreak = longIdle ? longIdleStreak + 1 : 0;`. ### B5: OVERLAP cannot start when the tag decode and pose time is longer than the inference time, although it gives a higher result rate
- Location: /home/user/photonvision-mltag/photon-core/src/main/java/org/photonvision/vision/pipeline/InferenceOverlapController.java:179
- Failure scenario: Two lanes, 60 FPS camera, 22 ms inference. The robot is near the tags when the controller is in SERIAL mode (start, or after a reset by a settings change or a pause of more than 500 ms), and the decode and pose time is 24 ms. SERIAL mode takes 46 ms for each frame = 21.6 FPS. In OVERLAP mode the inference of the next frames runs on the lanes while the work thread decodes, so the rate is 1 / 24 ms = 41.7 FPS. The OVERLAP branch (lines 191-212) has no such condition. The rate in OVERLAP is 1 / max(postInferenceAverage, inferenceAverage / lanes, camera period), the rate in SERIAL is 1 / (inference + post); OVERLAP is faster for each case with an inference time that is not near zero.
- Method from the review (use it unless the "Decisions" section above says something different): Do this only together with the depth limit of the third finding (without it the depth goes to 4 when the work thread is the limit).
